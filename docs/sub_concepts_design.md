# Sub-Concepts ("Sub-Encyclopedia") - Design

This document designs a **separate sub-concepts table** so that narrow,
numerous, or list-like topics -- chess openings (Sicilian Defense), individual
seasons of MLB teams (2004 Boston Red Sox season), small towns in Turkey
(Canova, Hafik), individual bird species -- can be tracked in the concepts
database without becoming part of the main encyclopedia. Sub-concepts live in
their own table but **share the Wikidata Q-id index**
(`concept_wikidata_index`) with main concepts. No body generation for these
entries is planned yet; the immediate value is being able to **filter them
out** of the main concept list, the Voverukas red-link rankings, and the
generation pipelines, while keeping a durable record (slug + Q-id + category)
of each topic.

The divide is by **prominence, not topic type**: a place, a chess topic, or a
sports topic is not automatically sub-encyclopedia material. Ankara merits a
main concept; the small district towns of Canova or Hafik do not, and those
are what the sub listing is for. Likewise "Chess" and "Boston Red Sox" are
main concepts even though individual openings and individual seasons file
under them as sub-concepts.

## Problem

Today a topic surfaced by the red-link ranker (or hand-picked by Q-id) has only
three possible states:

1. **Concept exists** - a full row in `concepts`, part of the main
   encyclopedia, seeds the rank graph, appears in the Barsukas list.
2. **Rejected** - `concept_wikidata_index.rejected = TRUE`; we never want a
   page for this Q-id.
3. **Untracked** - the topic keeps resurfacing at the top of the Voverukas
   wanted list on every run.

Topics like "Sicilian Defense" or "Hafik" fit none of these. They are real,
Q-id-resolvable, and might deserve short entries someday, but they should not
compete with "World War II" (or "Ankara") in the main encyclopedia, should not
be generated by default, and should stop clogging the wanted-topics report.

## Non-Goals (for now)

- No LLM body generation for sub-concepts (the table can grow a `body` column
  later without disturbing anything else).
- No change to `data/release` exports. Concepts and sub-concepts stay outside
  the lemma/GUID/release machinery, exactly as documented in
  `src/storage/models/concept.py`.
- No automatic Wikidata-based classification in the first phase (sketched
  under Future Work).

## Design Overview

Two pieces:

1. A new **`sub_concepts` table**: lightweight rows (slug + category +
   summary), stored in the same concepts database/backend as `concepts`, but
   kept out of every main-encyclopedia code path by construction. "Filing" a
   topic into the sub-encyclopedia simply means creating one of these cheap
   rows -- no separate pre-creation classification state is needed.
2. The existing **`concept_wikidata_index` is the shared Q-id spine**: a Q-id
   resolves to *either* a main concept *or* a sub-concept (or is rejected, or
   is merely cached). This keeps one canonical answer to "what do we know
   about this Q-id?" across both tables.

Sub-concept **categories** ("chess_opening", "bird_species", ...) get their
own hardcoded vocabulary. They are deliberately **not** added to the
`concept_type` vocabulary used by main concepts -- the two classification
axes never mix.

### Schema: the `sub_concepts` table

New model `SubConcept`, defined alongside `Concept` in
`storage/models/concept.py` (it reuses `normalize_concept_slug` and the same
`Base`/backend):

```python
class SubConcept(Base):
    """A sub-encyclopedia entry: a tracked topic that is deliberately NOT a
    main concept (e.g. a single chess opening, one team's season, one small
    town, one bird species). Exists primarily so these topics can be filtered
    out of main-encyclopedia listings, rankings, and generation.
    """

    __tablename__ = "sub_concepts"

    id: Mapped[int] = mapped_column(Integer, primary_key=True, autoincrement=True)

    # Canonical underscore-joined slug, same normalization and semantics as
    # Concept.slug. Unique within this table only; a slug may shadow a main
    # concept, in which case slug links resolve there (see Slug Semantics).
    slug: Mapped[str] = mapped_column(String, unique=True, nullable=False, index=True)

    # Required category from SUB_CONCEPT_CATEGORIES (hardcoded vocabulary,
    # separate from Concept.concept_type). Indexed for per-family listings.
    category: Mapped[str] = mapped_column(String, nullable=False, index=True)

    # One-sentence description, typically the Wikidata seed summary.
    summary: Mapped[Optional[str]] = mapped_column(Text, nullable=True)

    # Provenance / review metadata (mirrors conventions on Concept).
    verified: Mapped[bool] = mapped_column(Boolean, default=False, nullable=False)
    notes: Mapped[Optional[str]] = mapped_column(Text, nullable=True)

    added_at: Mapped[datetime.datetime] = mapped_column(TIMESTAMP, server_default=func.now())
    updated_at: Mapped[datetime.datetime] = mapped_column(
        TIMESTAMP, server_default=func.now(), onupdate=func.now()
    )
```

Deliberately absent for now: `body`, `sources`, `source_model`, `confidence`
(no generation), and `parent_slug` (grouping; see Deferred). Each can be added
later as a nullable column without a data migration.

### Schema: the shared Q-id index

`concept_wikidata_index` gains a second, mutually exclusive pointer:

```python
sub_concept_id: Mapped[Optional[int]] = mapped_column(
    Integer, ForeignKey("sub_concepts.id"), nullable=True, index=True
)

sub_concept: Mapped[Optional["SubConcept"]] = relationship("SubConcept")
```

with a table-level guard so a Q-id never points at both tables at once:

```python
CheckConstraint(
    "concept_id IS NULL OR sub_concept_id IS NULL",
    name="ck_wikidata_index_one_target",
)
```

(SQLite and Postgres both enforce CHECK constraints; the CRUD layer also
validates so JSONL and pre-migration databases behave identically.)

Effective states per Q-id, replacing today's three:

| State                       | Meaning                                        |
|-----------------------------|------------------------------------------------|
| `concept_id` set            | Main encyclopedia entry (unchanged)            |
| `sub_concept_id` set        | Sub-encyclopedia entry                         |
| `rejected = TRUE`           | Never want a page (unchanged)                  |
| all NULL, `title` cached    | Known Q-id, not yet triaged (unchanged)        |

Because filing a topic creates a real `sub_concepts` row immediately, there is
no "classified but rowless" limbo state to model in the index -- the row *is*
the classification. Idempotency for creation flows extends the existing check
in `storage/concept_service.py`: a Q-id whose index row has **either** pointer
set is already handled and is skipped (a sub-filed Q-id therefore cannot be
accidentally re-created as a main concept by a bulk run, and vice versa).

### Categories: a hardcoded vocabulary, separate from `concept_type`

`Concept.concept_type` keeps its existing free-form vocabulary ("person",
"event", ...) and does **not** gain entries like "chess_opening" or
"bird_species". Sub-concept categories are their own closed, hardcoded list --
the single source of truth for intake validation and the Barsukas category
select:

```python
# storage/models/concept.py (alongside SubConcept)

# Closed vocabulary for SubConcept.category. Extend by editing this tuple;
# these values are deliberately NOT part of Concept.concept_type.
SUB_CONCEPT_CATEGORIES: tuple = (
    "bird_species",
    "chess_concept",
    "sports_team_season",
)

# Strictly excluded categories: filing a Q-id under one of these actively
# records that we deliberately IGNORE the topic.
EXCLUDED_SUB_CONCEPT_CATEGORIES: tuple = ("micronation",)

ALL_SUB_CONCEPT_CATEGORIES: tuple = SUB_CONCEPT_CATEGORIES + EXCLUDED_SUB_CONCEPT_CATEGORIES
```

Naming notes: `chess_concept` is broader than just openings (endgames, motifs,
and other chess topics all file there). Species categories divide at roughly
the phylum/class level -- `bird_species` covers class Aves, and a future
`mammal_species` etc. would be a sibling entry rather than a widening of the
bird category. A place category is deferred until it is actually needed; when
added it should probably be named `small_town` rather than `city`, since it
covers minor places like Canova or Hafik while Ankara-scale cities stay in the
main encyclopedia.

A category never *claims* its whole topic type: filing is always a per-topic
prominence judgement. The prominent members of a family stay main concepts
(Ankara among Turkish places, "Chess" and "Boston Red Sox" above their
openings and seasons) while the long tail files here -- and `promote` /
`demote` move individual topics across the divide when a judgement changes.

CRUD validates `category` against `ALL_SUB_CONCEPT_CATEGORIES` (plain tuples
of strings rather than an `enum.Enum` keep this consistent with the
free-form-string style of the concept module while still being closed in
practice). Adding a new family of sub-topics is a one-line code change plus,
optionally, a Wikidata classification rule (Future Work).

#### Strictly excluded categories

The vocabulary is partitioned into **tracked** and **strictly excluded**
categories. A tracked category ("bird_species") means "real topic, deferred
from the main encyclopedia, maybe an entry someday". A strictly excluded
category ("micronation") means "we actively record that we ignore this topic
and its Q-id" -- the row exists precisely to note that decision, so the topic
never resurfaces for triage.

How exclusion differs from the per-Q-id `rejected` flag on the index:
`rejected` is an ad-hoc, uncategorized veto with no slug, no summary, and no
browsable page; an excluded sub-concept is a structured, categorized,
searchable record of the same decision, filed in bulk by family. New
family-wide exclusions should get a category; one-off vetoes can stay
`rejected`.

Behavioral consequences of an excluded category
(`SubConcept.is_excluded` / `is_excluded_sub_concept_category`):

- `promote_sub_concept` refuses (the Barsukas promote button is replaced by
  an explanatory note); the category must first be changed to a tracked one.
- `create_concept_from_qid` reports the Q-id as `exists` with detail
  "strictly excluded ..." rather than "filed as sub-concept ...".
- Voverukas suppression shows reason `excluded` instead of `sub-concept`.
- Everything else (never generated, never wanted, filterable, Q-id linked)
  is inherited from being a sub-concept at all.

### Alternatives considered

- **A `tier` column on `concepts`** (previous revision of this design) -
  rejected in review in favor of a separate table: main-encyclopedia queries,
  the rank graph, and generation flows stay correct *by construction* rather
  than by remembering to filter, and the main table doesn't accumulate
  thousands of body-less rows (there are far more bird species and
  small-town Q-ids than main topics).
- **Tag-based (`"sub"` in `Concept.tags` JSON)** - rejected. Not cheaply
  queryable or indexable on SQLite, invisible to constraints, easy to drift.
- **Index-only tracking (mark Q-ids in `concept_wikidata_index`, no row)** -
  insufficient: there would be nowhere to hang category/summary/notes, and
  red links that never get Q-id-resolved could not be matched by slug. The
  cheap `sub_concepts` row provides both.

### Slug and wiki-link semantics

Sub-concepts share the **slug conventions**: the same
`normalize_concept_slug` normalization, and no MediaWiki-style `Sub:` prefix.
Slugs are unique only *within* each table -- the same slug may exist in both
tables. Ambiguity is handled by two rules:

1. **Deterministic slug resolution**: a slug target resolves to the main
   concept first, then to a sub-concept with the same slug
   (`storage.queries.concept.resolve_wiki_link_targets`).
2. **Q-id wiki links for specificity**: ``[[Q103632]]`` (or piped
   ``[[Q103632|the Sicilian]]``) resolves through the shared Wikidata index
   to whichever table the Q-id points at, so a link can always target the
   sub-concept even when a main concept shadows its slug. Unpiped Q-id links
   display the resolved page title rather than the raw Q-id.

`[[Sicilian_Defense]]` inside a main concept body renders as a link to the
sub-concept's detail page (styled with a `wikilink-sub` class) rather than as
a red link. A slug that exists in *either* table is "existing" -- it can never
appear as a wanted page. Q-id-form targets are never wanted pages either: they
name a specific entity, not a creatable slug.

## Integration Points

### 1. Query layer (`storage/queries/concept.py`)

- `list_concepts` / `count_concepts` / `get_backlinks`: **unchanged**. The
  main list stays correct automatically because sub-concepts are not in the
  `concepts` table.
- New `list_sub_concepts(session, search="", category=None, limit=0,
  offset=0)` / `count_sub_concepts(...)` for the sub-encyclopedia view,
  with the same search semantics (slug + summary, space/underscore
  equivalence).
- `get_wanted_slugs`: the "existing" set becomes the union of `concepts.slug`
  and `sub_concepts.slug`, so filed sub-topics stop appearing as wanted
  pages.
- New helper `get_all_known_slugs(session) -> Set[str]` returning that union,
  shared by `get_wanted_slugs`, Voverukas, and the wiki-link renderer's
  `get_existing_link_targets`.

### 2. Voverukas ranking (`concepts/discovery.py`, CLI in `agents/vovere/voverukas.py`)

- **Graph/seed input**: only main concepts seed the rank graph and contribute
  edges (sub-concepts have no bodies). Unchanged code path.
- **Wanted-list output**: two filters on ranked red links:
  - drop slugs present in `sub_concepts` (via `get_all_known_slugs`); and
  - drop slugs whose cached `concept_wikidata_index` row (matched through the
    cached `title` via `normalize_concept_slug`) is `rejected` or points at a
    `sub_concept_id` -- this also closes the existing gap where rejected
    Q-ids still rank.
- A `--show-filtered` flag prints the suppressed items as a separate section
  of the report instead of hiding them, for triage review. The reason column
  distinguishes `rejected` (index flag), `sub-concept` (tracked category),
  and `excluded` (strictly excluded category).

Unresolved red links (no row anywhere) are by definition untriaged and
continue to rank normally; they leave the list when someone files them.

### 3. Creation / service layer (`storage/crud/concept.py`, `storage/concept_service.py`)

- New CRUD: `create_sub_concept(session, title, category, summary=None, ...)`
  (validates category against `ALL_SUB_CONCEPT_CATEGORIES`; the slug may
  shadow a main concept but must be unique among sub-concepts),
  `get_sub_concept_by_slug`, `update_sub_concept`, `delete_sub_concept`
  (detaches index rows so the Q-id reverts to untriaged).
- New index helper `link_wikidata_sub_concept(session, qid, sub_concept)`
  mirroring `link_wikidata_concept`, clearing `rejected` and enforcing the
  one-target rule (each refuses when the Q-id already points at the other
  table).
- New service `file_sub_concept_from_qid(session, qid, category)`: resolve
  the Q-id (cached seed), create the `SubConcept` row from title + summary,
  link the index. Idempotent: skips Q-ids whose index row already points at
  either table; when the slug also exists as a main concept the row is filed
  anyway with a warning detail (slug links resolve to the main concept).
- `create_concept_from_qid` / `create_concept_from_seed`: the existing
  "already linked" check extends to `sub_concept_id`, returning status
  `"exists"` with detail "filed as sub-concept" (or "strictly excluded" for
  excluded categories) so bulk main-concept runs skip sub-filed Q-ids loudly
  rather than silently.
- **Promotion/demotion**: promoting a sub-concept to a main concept =
  `create_concept(...)` + repoint the index row's target + delete the
  `sub_concepts` row, in one service function (`promote_sub_concept`), so
  the slug and Q-id never exist on both sides. Demotion is the mirror image.
  Both are curation actions exposed only in Barsukas. Promotion refuses
  strictly excluded sub-concepts; the category must be moved to a tracked one
  first.

### 4. Bulk intake (`concepts/seed/qids.py`, CLI in `agents/vovere/voveraite.py`)

Voveraite is the natural intake for hand-collected Q-id lists ("small towns in
Sivas Province", "chess openings", "MLB team seasons"). Add:

```
--sub --category chess_concept    # file these Q-ids as sub-concepts
--sub --category micronation      # record that these Q-ids are ignored
```

Behavior: resolve each Q-id, then call `file_sub_concept_from_qid` -- creating
the row and index link. No LLM calls are involved; `--sub` is mutually
exclusive with `--create`/`--batch`/`--no-body` (there is nothing to
generate). `--category` is required with `--sub` and validated against
`ALL_SUB_CONCEPT_CATEGORIES` at argparse time so a typo fails before any
network call.

Per project policy, Voveraite runs that resolve Q-ids make live
Wikidata/Wikipedia calls and need developer confirmation before running.

### 5. Barsukas UI (`barsukas/routes/concepts.py` + templates)

- **Main list page**: unchanged (no filtering needed).
- **New sub-encyclopedia section** under the concepts blueprint
  (`/concepts/sub`): list with search + category filter (ordinary GET form,
  select grouped into Tracked / Strictly excluded optgroups), plus a simple
  detail/edit page (category select, summary, notes, verified -- ordinary
  form submits, per house style). Excluded entries carry a red badge and an
  explanatory banner.
- **File Sub-Concept form** (`/concepts/sub/new`): takes a Wikidata Q-id
  (preferred; title/summary come from the seed via
  `file_sub_concept_from_qid`) or a manual title, plus the category select --
  the quick way to move a red link into the sub-encyclopedia.
- **Wiki-link rendering** (`barsukas/helpers/wikilinks.py`):
  `get_resolved_link_targets` resolves against both tables and Q-id targets
  (via `storage.queries.concept.resolve_wiki_link_targets`); links to
  sub-concepts route to the sub detail page with a `wikilink-sub` class.
- **Promote / demote** buttons on the respective detail pages (demote asks
  for a category and warns that the body/sources are discarded). The sub
  detail page flags when a main concept shadows the slug.

Barsukas changes need no tests per repo convention, but should be verified in
the developer's local browser.

## Schema rollout

Normal model initialization creates `sub_concepts` and adds the nullable
`concept_wikidata_index.sub_concept_id` column when missing. The CHECK
constraint applies to fresh databases via the model; for existing SQLite
databases the CRUD-layer validation is the effective guard.

No data backfill is required; filing existing topics as sub-concepts is a
curation activity, not a migration.

## Rollout Steps

Steps 1-4 are implemented (initial commit); step 5 remains future work.

1. **Schema** (done): `SubConcept` model, `SUB_CONCEPT_CATEGORIES`,
   `sub_concept_id` on the index, migration script, unit tests
   (`src/tests/storage/test_sub_concepts.py`).
2. **Service threading** (done): `file_sub_concept_from_qid`,
   `promote_sub_concept` / `demote_concept_to_sub`, `get_all_known_slugs`,
   `resolve_wiki_link_targets`, extended "already linked" checks in
   `create_concept_from_qid`.
3. **Agents** (done): Voverukas wanted-list filtering (sub slugs + rejected +
   sub-linked Q-ids + Q-id-form targets) with `--show-filtered`; Voveraite
   `--sub --category`.
4. **Barsukas** (done): sub-encyclopedia list/detail/form, wiki-link
   rendering across both tables and Q-id targets, promote/demote.
5. **Future** (separate designs): Wikidata auto-classification, `parent_slug`
   grouping, sub-concept body generation (likely shorter/templated bodies).

## Future Work: Wikidata auto-classification

Most sub-concept categories are cleanly identifiable from Wikidata claims, so
a rule table could classify topics at seed-fetch time:

| Category             | Signal (illustrative)                                    |
|----------------------|----------------------------------------------------------|
| `chess_concept`      | P31 (instance of) = chess opening / chess term           |
| `sports_team_season` | P31 = season of a sports club                            |
| `bird_species`       | P31 = taxon with P105 (taxon rank) = species, class Aves |
| `small_town` (future)| P31 = town/village (+ P17 country); needs a prominence cut (population, capital/province status) so Ankara-scale cities are never auto-filed |

A curated mapping of P31 class Q-ids to a `SUB_CONCEPT_CATEGORIES` entry --
hardcoded next to the category tuple -- would let `fetch_wikidata_concept_seed`
return a suggested category alongside the seed, turning triage into
accept/decline. This is deliberately out of scope for phase 1: it changes what
the seed fetch requests from Wikidata (live API calls, developer confirmation
required) and needs a review loop so misclassifications are cheap to fix.

## Open Questions

1. **Do sub-concepts ever get bodies?** If the sub-encyclopedia later wants
   short templated entries, `sub_concepts` grows `body`/`sources`/
   `source_model` columns and a dedicated (cheaper) generation flow;
   wiki links inside sub bodies would then need a decision about whether
   they feed the rank graph.
2. **Lemma links to sub-concepts.** Some sub-topics are also headwords (a
   bird species like "chaffinch" is a lemma). `ConceptLemmaLink` stores only
   a Q-id, so it is already target-agnostic; recommendation: allow links to
   sub-filed Q-ids and revisit only if release exports need to distinguish.
3. **Category granularity.** Is a future `small_town` one category, or should
   intake batches carry a finer note ("towns in Sivas Province") in `notes`?
   Recommendation: keep the vocabulary coarse and put the batch context in
   `notes`, so the hardcoded list stays short. The prominence line itself
   (Hafik files, Ankara does not) is a filing judgement, not something the
   category encodes.
