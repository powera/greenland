# Sub-Concepts ("Sub-Encyclopedia") - Design

This document designs a **tier** system for concepts so that narrow, numerous,
or list-like topics -- chess openings (Sicilian Defense), individual seasons of
MLB teams (2004 Boston Red Sox season), cities in Turkey, individual bird
species -- can be tracked in the concepts database without becoming part of the
main encyclopedia. No body generation for these entries is planned yet; the
immediate value is being able to **filter them out** of the main concept list,
the Voverukas red-link rankings, and the generation pipelines, while keeping a
durable record (slug + Wikidata Q-id) of each topic.

## Problem

Today a topic surfaced by the red-link ranker (or hand-picked by Q-id) has only
three possible states:

1. **Concept exists** - a full row in `concepts`, part of the main
   encyclopedia, seeds the rank graph, appears in the Barsukas list.
2. **Rejected** - `concept_wikidata_index.rejected = TRUE`; we never want a
   page for this Q-id.
3. **Untracked** - the topic keeps resurfacing at the top of the Voverukas
   wanted list on every run.

Topics like "Sicilian Defense" or "Ankara" fit none of these. They are real,
Q-id-resolvable, and might deserve short entries someday, but they should not
compete with "World War II" in the main encyclopedia, should not be generated
by default, and should stop clogging the wanted-topics report.

## Non-Goals (for now)

- No LLM body generation for sub-concepts (schema allows it later).
- No change to `data/release` exports. Concepts stay outside the
  lemma/GUID/release machinery, exactly as documented in
  `src/storage/models/concept.py`.
- No automatic Wikidata-based classification in the first phase (sketched
  under Future Work).

## Design Overview

Add a single new axis, **tier**, orthogonal to the existing `concept_type`
classification:

- `tier` says *how prominent* a topic is: `"main"` (the encyclopedia as it
  exists today) or `"sub"` (the sub-encyclopedia).
- `concept_type` continues to say *what kind of thing* it is:
  `"chess_opening"`, `"sports_team_season"`, `"city"`, `"bird_species"`, ...

Sub-concepts are ordinary rows in the existing `concepts` table (same storage,
same slug namespace, same Q-id index), distinguished only by their tier. A
parallel nullable tier on `concept_wikidata_index` lets a Q-id be classified as
sub-tier *before* any concept row exists, which is what makes red-link
filtering work.

### Schema changes

**1. `concepts.tier`** (new column)

```python
# Prominence tier: "main" = the primary encyclopedia; "sub" = the
# sub-encyclopedia (narrow/list-like topics tracked but not generated by
# default). Use the CONCEPT_TIER_* constants.
tier: Mapped[str] = mapped_column(
    String, nullable=False, default=CONCEPT_TIER_MAIN, index=True
)
```

With module-level constants in `storage/models/concept.py`:

```python
CONCEPT_TIER_MAIN: str = "main"
CONCEPT_TIER_SUB: str = "sub"
CONCEPT_TIERS: frozenset[str] = frozenset({CONCEPT_TIER_MAIN, CONCEPT_TIER_SUB})
```

A string rather than a boolean costs nothing extra and leaves headroom for
future tiers (e.g. a `"list"` tier for pure index pages) without another
migration.

**2. `concept_wikidata_index.tier`** (new nullable column)

```python
# Prominence tier assigned to this Q-id, mirroring Concept.tier. May be set
# while concept_id is still NULL: "this topic is sub-encyclopedia material;
# do not rank it as a main wanted topic or create it as a main concept."
# NULL means unclassified (treated as main-tier by default).
tier: Mapped[Optional[str]] = mapped_column(String, nullable=True)
```

This gives the reverse index three effective states per Q-id, replacing
today's two:

| State                  | Meaning                                          |
|------------------------|--------------------------------------------------|
| `rejected = TRUE`      | Never want a page (unchanged)                    |
| `tier = "sub"`         | Track it; belongs to the sub-encyclopedia        |
| `tier IS NULL`         | Unclassified; eligible for the main encyclopedia |

When a concept is later created for a Q-id whose index row says
`tier = "sub"`, the concept **inherits** that tier automatically (see
Creation Paths below), so a bulk run cannot accidentally promote a
sub-classified topic into the main encyclopedia.

**3. Deferred: `concepts.parent_slug`**

Grouping sub-concepts under a main concept ("2004_Boston_Red_Sox_season" ->
"Boston_Red_Sox"; each bird species -> "Bird") would be a nullable, non-FK
`parent_slug` column following the `ConceptLemmaLink.concept_slug` convention.
It is not needed for filtering -- `concept_type` already supports coarse
grouping -- so it is deferred until a sub-encyclopedia browsing UI wants it.

### Alternatives considered

- **Separate `sub_concepts` table** - rejected. It would duplicate the slug
  namespace, CRUD, the Q-id index, and wiki-link resolution, and promoting a
  sub-concept to main (or back) would become a row move across tables instead
  of a one-column update.
- **Tag-based (`"sub"` in `Concept.tags` JSON)** - rejected. Not cheaply
  queryable or indexable on SQLite, invisible to unique constraints, and easy
  to drift; tier is a first-class query dimension for every list and ranking
  path.
- **Index-only tracking (no Concept row until generation)** - insufficient
  alone. Sub-topics should live "in the same place as the main concepts" so
  they can be browsed, linked via `[[...]]`, and carry
  `concept_type`/`notes`/`sources`. But the index tier *is* also required,
  because red-link filtering must work before any row exists. The design uses
  both: index tier is the pre-creation state, concept tier is the durable one.

### Slug and wiki-link semantics (unchanged)

Sub-concepts share the single slug namespace. `[[Sicilian_Defense]]` inside a
main concept body resolves to the sub-concept page like any other link; there
is no MediaWiki-style `Sub:` prefix, so `normalize_concept_slug`,
`WIKI_LINK_RE`, and `parse_wiki_links` are untouched. Once a sub-concept row
exists, its slug counts as "existing" everywhere -- it can never reappear as a
red link or wanted page.

## Integration Points

### 1. Query layer (`storage/queries/concept.py`)

`_filtered_concepts_query` / `list_concepts` / `count_concepts` gain an
optional `tier` parameter:

```python
def list_concepts(
    session, search="", verified_only=False, tier=None, limit=0, offset=0
): ...
```

`tier=None` preserves today's behavior (all rows). The Barsukas main list
passes `tier="main"` by default; a new sub-encyclopedia view passes
`tier="sub"`. Because existing rows are backfilled to `"main"`, main-tier
filtering is exact, not "main or NULL".

`get_wanted_slugs` and `get_backlinks` need no change: sub-concepts are rows,
so they are already "existing" for wanted-page purposes, and backlinks across
tiers are desirable.

### 2. Voverukas ranking (`agents/vovere/voverukas.py`)

Two touch points in `rank_wanted` / the CLI:

- **Graph/seed input**: unchanged. All concepts (both tiers) load into
  `existing_slugs`, so sub-concepts never appear as wanted. Their (currently
  empty) bodies contribute no edges; if sub-concepts gain bodies later this
  choice can be revisited.
- **Wanted-list output**: after ranking, drop wanted items whose slug matches
  a classified index row. The lookup goes through the cached
  `concept_wikidata_index.title` (compared via `normalize_concept_slug`),
  which the existing `--resolve-qids` flow already populates. Filter out rows
  with `rejected = TRUE` (a gap today) and `tier = "sub"` alike. A
  `--include-sub` flag prints the filtered sub-tier items as a separate
  section of the report instead of hiding them.

Unresolved red links (no cached Q-id yet) are by definition unclassified and
continue to rank normally; classification happens when someone resolves and
triages them.

### 3. Creation paths (`storage/concept_service.py`, `storage/crud/concept.py`)

- `create_concept(...)` gains `tier: str = CONCEPT_TIER_MAIN` (validated
  against `CONCEPT_TIERS`); `update_concept(...)` gains an optional `tier`.
- `create_concept_from_qid` / `create_concept_from_seed` gain
  `tier: Optional[str] = None` meaning "inherit": if the Q-id's index row
  carries `tier = "sub"`, the created concept is sub-tier regardless of the
  caller; an explicit argument overrides. `link_wikidata_concept` keeps the
  index row's tier in sync with the concept.
- Generation defaults: agent flows that generate bodies (Vovere via
  Voverukas `--create`/`--batch`) operate on main-tier topics only, because
  sub-tier items are already filtered out of their input. Voveraite (explicit
  Q-ids) gains the tier flag described next, and refuses to *generate* bodies
  for sub-tier creations until sub-generation is designed.

### 4. Bulk intake (`agents/vovere/voveraite.py`)

Voveraite is the natural intake for hand-collected lists ("all cities in
Turkey", "chess openings", "MLB team seasons"). Add:

```
--tier sub          # classify these Q-ids as sub-encyclopedia
```

Behavior with `--tier sub`:

- Default (no `--create`): resolve each Q-id, cache its title, and set
  `concept_wikidata_index.tier = "sub"`. No concept rows. This is the
  cheapest way to make the ranker stop suggesting a family of topics.
- With `--create --no-body`: additionally create bodiless sub-tier concept
  rows (slug + summary + sources from the seed), for topics we want browsable
  now.
- `--batch`, and `--create` without `--no-body`, are rejected with `--tier
  sub` for now (no sub-body generation yet).

A small companion helper in `storage/crud/concept.py`
(`set_wikidata_tier(session, qid, tier)`) backs both Voveraite and the
Barsukas actions.

Per project policy, Voveraite runs that resolve Q-ids make live
Wikidata/Wikipedia calls and need developer confirmation before running.

### 5. Barsukas UI (`barsukas/routes/concepts.py` + templates)

- **List page**: a tier filter (ordinary GET form select: Main / Sub / All)
  defaulting to Main; sub rows show a badge next to the existing
  `concept_type` badge. Counts split accordingly.
- **Detail/edit**: tier appears as a select on the edit form (ordinary form
  submit, per house style). A concept can be demoted/promoted at any time;
  the linked index row follows.
- **Wanted/triage views**: wherever ranked wanted topics are surfaced, add a
  "mark as sub" action (form POST) that calls `set_wikidata_tier` -- this is
  the one-click way to file a red link into the sub-encyclopedia without
  creating anything.
- **New sub-encyclopedia section**: the same list template filtered to
  `tier="sub"`, linked from the concepts index. Nothing fancier until
  sub-concepts have bodies.

Barsukas changes need no tests per repo convention, but should be verified in
the developer's local browser.

## Migration

`src/storage/migrations/add_concept_tier.py`, following the
`add_concept_wikidata_index_title.py` pattern (idempotent, backend-agnostic,
`--postgres` / `--dry-run` flags):

1. `ALTER TABLE concepts ADD COLUMN tier` (String), backfill existing rows to
   `'main'`, then enforce NOT NULL / default per backend capabilities (SQLite
   adds the column with a default; Postgres sets `DEFAULT 'main' NOT NULL`).
2. `ALTER TABLE concept_wikidata_index ADD COLUMN tier` (String, nullable).
3. Index on `concepts.tier` (created by `create_all` on fresh databases;
   created explicitly here for existing ones).

Fresh databases get everything from `Base.metadata.create_all` automatically.
No data backfill beyond the `'main'` default is required; classifying existing
topics as sub is a curation activity, not a migration.

## Rollout Steps

1. **Schema**: model constants, both `tier` columns, migration script, unit
   tests for tier validation in CRUD.
2. **Query + service threading**: `list_concepts`/`count_concepts` tier
   filter; `create_concept`/`update_concept`/`create_concept_from_qid` tier
   handling with index inheritance; `set_wikidata_tier` helper.
3. **Agents**: Voverukas wanted-list filtering (`rejected` + `tier="sub"`)
   with `--include-sub`; Voveraite `--tier sub` intake.
4. **Barsukas**: list filter + badge, edit-form tier select, "mark as sub"
   triage action, sub-encyclopedia list view.
5. **Future** (separate designs): Wikidata auto-classification, `parent_slug`
   grouping, sub-concept body generation (likely shorter/templated bodies).

## Future Work: Wikidata auto-classification

Most sub-tier families are cleanly identifiable from Wikidata claims, so a
rule table could classify topics at seed-fetch time:

| Family              | Signal (illustrative)                                  |
|---------------------|--------------------------------------------------------|
| Chess openings      | P31 (instance of) = chess opening                      |
| Team seasons        | P31 = season of a sports club                          |
| Cities in a country | P31 = city (+ P17 country qualifier)                   |
| Bird species        | P31 = taxon with P105 (taxon rank) = species, class Aves |

A curated mapping of P31 class Q-ids to `(tier, concept_type)` -- stored as a
small table or a constant module -- would let `fetch_wikidata_concept_seed`
return a suggested tier alongside the seed. This is deliberately out of scope
for phase 1: it changes what the seed fetch requests from Wikidata (live API
calls, developer confirmation required) and needs a review loop so
misclassifications are cheap to fix.

## Open Questions

1. **Should sub-concepts ever seed rank?** Once sub-concepts have bodies,
   their outbound links could disperse rank into the main graph. Current
   answer: they are graph nodes but effectively inert (empty bodies);
   revisit alongside sub-body generation.
2. **Lemma links to sub-concepts.** Some sub-topics are also headwords (a
   bird species like "chaffinch" is a lemma). Recommendation: allow
   `ConceptLemmaLink` to point at sub-tier concepts -- the link stores only
   the Q-id and is tier-agnostic -- and revisit only if release exports need
   to distinguish tiers.
3. **Additional tiers.** `"list"` (pure index pages) or `"stub"` may be
   wanted later; the string column and `CONCEPT_TIERS` constant make that a
   constant-and-UI change, not a schema change.
